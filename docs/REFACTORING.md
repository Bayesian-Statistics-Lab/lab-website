# 유지보수를 위한 단계별 리팩토링

기존 기능·권한·성능 최적화를 유지하면서 책임을 분리합니다. 기능 개선, 스키마 변경, 캐시 조정, 라이브러리 교체는 리팩토링 PR과 분리합니다. 검증한 작은 변경을 PR 단위로 검토하고 다음 도메인으로 확장합니다.

## 단계와 범위

| 단계 | 범위 | 상태 / 완료 조건 |
| --- | --- | --- |
| 1 | 논문 공개 상태 변경·선택 삭제 API, 화면의 논문 API 호출·공개 상태 표시 | 별도 브랜치에서 구현, 회귀 테스트·타입·빌드 검증 후 PR |
| 2 | 논문 목록·편집 뷰와 상태 훅, Scholar 가져오기 | 1단계 검토 후; 목록 조회·검색·정렬·선택·100개 배치 삭제 계약 유지 |
| 3 | 게시글·고정 본문·연혁·연구 분야 | 조회와 변경을 나누고 작성자 권한·페이지별 편집·캐시 계약을 먼저 테스트 |
| 4 | 구성원·가입 승인·계정 | RPC 트랜잭션·RLS·관리자 보호·가입 복구를 유지; 별도 테스트 DB에서 검증 |
| 5 | 미디어·공통 UI·스타일 | private Storage, 직접 전송, 공개 참조 공유 캐시, 리사이징·GIF·반응형 검증 후 정리 |

이 순서는 제안이며 뒤 단계는 아직 수행하지 않았습니다. 단계별 변경을 검토하기 전에 전체 도메인을 한 번에 옮기지 않습니다.

## 1단계의 책임 분리

| 위치 | 책임 | 의존성 |
| --- | --- | --- |
| `app/api/v1/admin/publications/*/route.ts` | HTTP 경로·메서드 연결 | 컨트롤러 |
| `server/publications/publication.controller.ts` | 관리자 인증, JSON/DTO 검증, HTTP 응답, 변경 후 캐시 무효화 | 서비스·리포지토리 조립, Next.js |
| `server/publications/publication.service.ts` | 공개 상태 변경과 삭제의 처리 순서, 중복 ID 제거, 실제 변경·부분 성공 판단 | 리포지토리 인터페이스; HTTP·Supabase 런타임에 의존하지 않음 |
| `server/publications/publication.repository.ts` | Supabase 쿼리와 DB 오류 전달 | 호출자가 제공한 인증된 DB 클라이언트 |
| `server/publications/publication.entity.ts` | 이 유스케이스의 논문 ID·상태 타입, 요약 설정 식별 규칙 | 외부 의존성 없음 |
| `server/publications/publication.dto.ts` | 요청 스키마와 응답 타입 | Zod와 도메인 타입 |
| `features/publications/api/publication-client.ts` | 논문 HTTP 호출·응답·오류 전달 | fetch; DTO/엔터티는 타입만 참조 |
| `features/publications/components/PublicationStatusControl.tsx` | 공개 스위치·상태 표시 | props만 사용, 조회·변경 요청 없음 |
| `components/AdminEditor.tsx` | 기존 편집 상태·선택·배치 처리·확인창·메시지 조율 | 위 API 클라이언트와 표시 컴포넌트 |

엔터티는 필요한 필드만 모델링합니다. DB 행 전체를 억지로 클래스에 감싸거나 실행 시 DI 컨테이너를 추가하지 않습니다. 객체 생성은 컨트롤러에서 하고 서비스는 인터페이스를 주입받습니다. 스키마의 테이블·열 이름과 공개 API 경로는 계약이므로 명시적으로 유지하며, 반복되는 논문 요약 식별 규칙은 한 곳에서 관리합니다. 프론트엔드의 DTO 참조는 `import type`으로 서버 코드·Zod를 클라이언트 번들에 추가하지 않습니다.

`lib/deletion.ts`의 기존 논문 삭제 export는 호환 어댑터로 남겨 기존 호출·테스트를 유지합니다. 게시글·구성원 삭제 구현은 이 단계에서 이동하지 않습니다.

## 보존해야 하는 계약

| 상황 | 기존·리팩토링 후 동작 |
| --- | --- |
| 관리자 아님 | 본문 처리 전 401, `requireAdmin()` 유지 |
| 잘못된 JSON·UUID·상태 / 삭제 ID 0개·101개 이상 | 400, 기존 한국어 오류 메시지 유지 |
| 상태 변경 DB 오류 또는 변경된 행 없음 | 400; 요약 변경·캐시 무효화 없음 |
| 논문 상태 변경 성공, 요약 변경 실패 | 500; 논문은 변경되었으므로 기존 캐시 태그·경로 무효화 |
| 삭제 DB 오류 | 500; 요약 정리·캐시 무효화 없음 |
| 실제 삭제 행 없음 | 409; 성공으로 처리하지 않음 |
| 일부 삭제 | 실제 삭제 ID만 요약 정리, 200과 기존 warning 반환 |
| 요약 정리 실패 | 삭제 ID 유지, 기존 정리 실패 warning을 우선 반환, 캐시 무효화 |
| 정상 변경 | `lab-public` 태그와 `/` layout 무효화, 기존 응답 모양 유지 |
| 프론트엔드 삭제 | 기존 100개씩 순차 요청, 각 배치 직후 목록·선택 갱신, 경고·실패 처리 유지 |
| 공개 스위치 | 기존 DOM 클래스·접근성 이름·disabled·변경 중 표시 유지 |

DB 쿼리 수·순서, 인증된 클라이언트/RLS, 응답 코드·메시지, 캐시 TTL·태그, 목록 조회와 동적 에디터 로딩을 바꾸지 않습니다. CSS, 업로드 경로·압축, 이미지 최적화, 공개 미디어 캐시는 이 단계의 변경 대상이 아닙니다.

## 검증

- 기존 테스트 57개와 신규 논문 관리 테스트 9개: 총 66개.
- 신규 테스트: DTO 경계, 상태/요약 처리 순서, DB 오류·0행, 부분 변경·삭제, 중복 ID·실제 삭제 ID 정리, 클라이언트 요청 계약·오류 전달.
- 기존 논문 삭제 쿼리 테스트는 호환 어댑터를 거쳐 새 리포지토리를 검사합니다.
- `npm run typecheck`, `npm test`, `npm run build`를 순서대로 실행합니다. 타입 검사와 빌드는 `.next/types`를 공유하므로 동시에 실행하지 않습니다.
- 운영 DB 실제 삭제나 가입·탈퇴는 검증 목적으로 실행하지 않습니다. 관리자 로그인 화면의 실제 토글·삭제·뒤로 가기는 별도 운영/테스트 DB 확인 대상입니다.

## 다음 작업 기준

다음 PR은 논문 목록·폼의 상태와 뷰를 분리합니다. `AdminEditor` 전체를 한 번에 다시 쓰지 않고 선택·정렬·폼 전환·경고·부분 삭제 처리를 먼저 테스트할 수 있도록 옮깁니다. 공통 훅·기본 저장소·서비스 프레임워크는 실제로 두 도메인 이상에서 공통 책임이 확인된 뒤 도입합니다. 고정값을 무조건 설정 파일로 이동하는 것보다 변경 이유와 소유 도메인을 분명히 하는 데 집중합니다.

운영 반영 시 PR 단위로 되돌릴 수 있습니다. 이 단계에는 DB 마이그레이션이나 새 의존성이 없습니다.
